Версія: 0.1  
Дата: 07.11.2026  
Статус: DRAFT — на перевірку; погодження студентом не зафіксовано.

## 1. Джерело та правила використання

Продуктове джерело: **SD_Spec.docx.pdf** (специфікація SD_Spec, надана у PDF). Прочитано розділи 0–9. Розділ 9 містить лише заголовок UX/UI & Interaction Design.

Методичні рекомендації визначають процес роботи, але не замінюють продуктових вимог. Приклади іншої роботи не є джерелом вимог або доказами виконання нашої роботи.

Позначення:
- **SOURCE** — безпосередня вимога специфікації.
- **DERIVED** — висновок із зазначених вимог.
- **PROPOSED** — запропоноване рішення, ще не обов’язкове.
- **UNRESOLVED** — питання без зафіксованого рішення людини.

Оригінальні US/AC/BR/NFR-ID збережено. Чотири ненумеровані критерії US-03 позначено посиланнями на пункти, без вигаданих AC-ID. Gherkin-приклади не рахуються повторно як додаткові AC.

## 2. Призначення та користувачі

**SOURCE.** Mini Issue Tracker — внутрішня вебсистема для невеликої команди розробників: реєстрація проблем, визначення відповідальних і пріоритетів, відстеження стану та обговорення заявок. Бізнес-мета — скоротити час від реєстрації проблеми до призначення та вирішення. Джерело: §1, Problem Statement, Product Business goal; §2, Product Vision.

**SOURCE.** Основні користувачі: Team Member та Team Lead. У першій версії є три заздалегідь визначені користувачі: два Team Member та один Team Lead. Користуватися системою можуть лише автентифіковані члени команди. Джерело: §1, Primary users, Open Questions; §3, BR-01.

**SOURCE.** Product Owner та System Administrator — другорядні зацікавлені сторони, які не беруть безпосередньої участі в основних сценаріях MVP. Джерело: §1, Stakeholders.

**SOURCE.** Система призначена для внутрішньої невеликої команди; перший реліз має бути простим web application. Зовнішні клієнти не є користувачами. Джерело: §1, KC-01–KC-04.

## 4. Included User Stories та всі критерії приймання

Усі рядки критеріїв нижче мають тип **SOURCE**. Формулювання скорочено без зміни змісту.

### US-01 — Create Issue

Actor: член команди. Мета: створити заявку з назвою й описом для реєстрації та відстеження проблеми. Джерело: §5, US-01; автентифікація — §3, BR-01/02.

| ID | Критерій |
|---|---|
| AC-01.1 | Користувач може ввести Title та Description |
| AC-01.2 | Title є обов’язковим |
| AC-01.3 | Description є обов’язковим |
| AC-01.4 | Після створення заявка отримує ID, status = Open, created_at та author |
| AC-01.5 | Після створення priority не встановлено |

Джерело: §5, US-01, AC-01.1–AC-01.5.

**SOURCE.** Gherkin-приклад: порожній Title → заявка не створюється, повідомлення «Title is required». Приклад успішного створення містить унікальний ID та поточного користувача як автора. Джерело: §5, US-01, Gherkin-сценарії. Це приклади наявних AC, а не додаткові критерії.

### US-02 — View Issues

Actor: автентифікований член команди. Мета: переглядати зареєстровані заявки та їхні поточні деталі. Джерело: §5, US-02.

| ID | Критерій |
|---|---|
| AC-02.1 | Користувач може переглянути список зареєстрованих issues |
| AC-02.2 | У списку для кожного issue показано щонайменше ID, Title, Status, Priority та Assignee, якщо призначений |
| AC-02.3 | Користувач може вибрати issue зі списку та відкрити його деталі |
| AC-02.4 | Деталі містять ID, Title, Description, Status, Priority, Assignee за наявності, Author та Created at |
| AC-02.5 | За відсутності issues показано порожній список або повідомлення про їх відсутність |

Джерело: §5, US-02, AC-02.1–AC-02.5.

### US-03 — Assign Issue to the responsible team member

Actor: Team Lead. Мета: визначити відповідального за виконання заявки. Джерело: §5, US-03.

| Вихідне посилання | Критерій |
|---|---|
| US-03, AC, пункт 1 | Можна вибрати одного assignee |
| US-03, AC, пункт 2 | Assignee повинен бути членом команди |
| US-03, AC, пункт 3 | Призначати заявку може лише Team Lead |
| US-03, AC, пункт 4 | Поточний assignee відображається у заявці |

Джерело: §5, US-03, чотири ненумеровані пункти Acceptance Criteria.

### US-04 — Set Issue Priority

Actor: Team Lead. Мета: встановлювати пріоритет для визначення порядку роботи. Джерело: §5, US-04.

| ID | Критерій |
|---|---|
| AC-04.1 | Допустимі встановлені значення Priority: Low, Normal, High, Critical |
| AC-04.2 | Встановлювати та змінювати priority може лише Team Lead |

Джерело: §5, US-04, AC-04.1–AC-04.2.

### US-05 — Track Issue Progress

Actor: член команди. Мета: бачити поточний стан роботи над проблемою. Джерело: §5, US-05.

| ID | Критерій |
|---|---|
| AC-05.1 | Поточний status відображається для кожного issue |
| AC-05.2 | Status відображається на сторінці issue |
| AC-05.3 | Status відображається у списку issues |

Джерело: §5, US-05, AC-05.1–AC-05.3.

### US-06 — Add Comment

Actor: член команди. Мета: обговорювати проблему в контексті заявки. Джерело: §5, US-06.

| ID | Критерій |
|---|---|
| AC-06.1 | Текст коментаря не може бути порожнім |
| AC-06.2 | Доданий коментар зберігається та показується для відповідного issue |
| AC-06.3 | Автор коментаря зберігається та відображається |
| AC-06.4 | Дата й час створення коментаря зберігаються та відображаються |
| AC-06.5 | Невдале збереження не створює коментар і супроводжується повідомленням про помилку |

Джерело: §5, US-06, AC-06.1–AC-06.5.

### US-07 — Update Issue Status

Actor: поточний виконавець заявки. Мета: змінювати статус, щоб команда бачила стан виконання. Джерело: §5, US-07.

| ID | Критерій |
|---|---|
| AC-07.1 | Нова заявка створюється зі статусом Open |
| AC-07.2 | Допустимі статуси: Open, In Progress, Resolved, Closed |
| AC-07.3 | Після зміни новий статус зберігається та відображається під час наступного перегляду |
| AC-07.4 | Користувач, який не є виконавцем заявки, не може змінювати її статус |
| AC-07.5 | Не можна встановити статус поза визначеним переліком |

Джерело: §5, US-07, AC-07.1–AC-07.5. Обмеження переходів додатково визначено у §3, BR-08.1.

### US-08 — View Important Open Issues

Actor: член команди. Мета: швидко знаходити важливі заявки, що потребують уваги. Джерело: §5, US-08.

| ID | Критерій |
|---|---|
| AC-08.1 | High зі статусом, відмінним від Closed, відображається в Important Issues |
| AC-08.2 | Critical зі статусом, відмінним від Closed, відображається в Important Issues |
| AC-08.3 | Low та Normal не відображаються в Important Issues |
| AC-08.4 | Closed не відображається незалежно від priority |

Джерело: §5, US-08, AC-08.1–AC-08.4.

## 5. UI-релевантні правила

| Тип | Правило | Джерело |
|---|---|---|
| SOURCE | Доступ — лише для автентифікованих членів команди; створення доступне кожному з них | §3, BR-01/02 |
| SOURCE | Початковий status = Open | §3, BR-03 |
| SOURCE | Початковий priority відсутній (Not Set); встановлені рівні — Low, Normal, High, Critical | §3, BR-04/05 |
| SOURCE | Керувати priority може лише Team Lead | §3, BR-06 |
| SOURCE | Призначати одного члена команди виконавцем може лише Team Lead | §1, Open Questions; §5, US-03, AC, пункти 1–3 |
| SOURCE | Status: Open, In Progress, Resolved, Closed | §3, BR-07 |
| SOURCE | Status змінює відповідальний виконавець; non-assignee цього робити не може | §3, BR-08; §5, AC-07.4 |
| SOURCE | Лише чотири переходи: Open → In Progress; In Progress → Resolved; Resolved → Closed; Resolved → In Progress | §3, BR-08.1 |
| SOURCE | Важливі пріоритети — High та Critical | §3, BR-09 |
| SOURCE | Resolved ще не Closed; за відповідного priority заявка залишається серед Important Issues | §3, BR-09.1; §5, AC-08.1/2 |
| SOURCE | Issues не видаляються | §3, BR-10 |
| SOURCE | Окрема користувацька історія змін не передбачена | §3, BR-11 |
| SOURCE | Коментар: непорожній текст, автор, дата й час; помилка збереження не створює коментар | §5, AC-06.1–AC-06.5 |

**DERIVED.** Team Lead також повинен бути поточним assignee для зміни статусу. Підстава: BR-08 та AC-07.4; винятку для ролі керівника немає.

**DERIVED.** За відсутності assignee ніхто не відповідає умові зміни статусу. Підстава: BR-08 та AC-07.4. Початкова відсутність assignee ще потребує рішення Q-02.

**DERIVED.** Closed не має дозволених вихідних переходів. Це не означає автоматичну заборону коментарів або інших незалежних дій. Підстава: BR-08.1; US-06.

**DERIVED.** Предикат Important Issues: `Priority ∈ {High, Critical} AND Status ≠ Closed`. Not Set не задовольняє його; Resolved за High/Critical задовольняє. Підстава: BR-04/05, BR-09/09.1, AC-08.1–AC-08.4. Слово Open у назві US-08 не обмежує вибірку лише статусом Open.

**SOURCE.** Якщо AI-функції реалізовуватимуться в майбутньому, рекомендації не мають автоматично змінювати category/priority без дії користувача. У поточний дизайн вони не включаються. Джерело: BR-12; §8, Future.

Усі Q мають тип і статус **UNRESOLVED**. Рекомендовані варіанти винесено до Decision_Log.md зі статусом PROPOSED.
